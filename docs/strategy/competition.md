# Competitive landscape

Primary sources reviewed September 18, 2026. These are first-party descriptions, not independent performance validation. Feature absence from the reviewed pages is not proof that a competitor lacks it. Recheck before external pitching: this category changes quickly.

## Additional adjacent project found during naming review

[Weft by spranab](https://github.com/spranab/weft) describes an autonomous-agent execution ledger with signed provenance, recorded read sets, stale-read rejection, and MCP integration. Its claims are first-party descriptions, not an independently verified benchmark. This materially overlaps our motivating failure; avoid claiming stale-assumption detection is unique. Loomplane’s proposed adoption advantage is a smaller context layer alongside existing Git and agent workflows, which still needs comparative testing. This exact name collision also prompted the [Loomplane naming decision](naming.md).

## The question our evaluation must answer

Can a team using different agents reliably answer all four questions without manual log archaeology?

1. Which declared assumptions did this task’s packet contain, at exactly which revisions?
2. Which in-flight consumers were affected when an assumption changed?
3. Was the change intentionally pinned, refreshed, or reviewed as compatible?
4. Did the affected output get revalidated before completion?

The current Loomplane prototype handles revision records, transitive drift, intentional pins, and receipt completion checks. Questions 3 and 4 still require evidence of actual review and code revalidation; refreshing a packet or recording a receipt does not establish either. The reviewed sources demonstrate substantial overlapping primitives; they do not establish that nobody else can answer this sequence. Our edge must be validated on the complete workflow.

## Competitive response rules

- If native IDE coordination is enough, focus pilots on genuinely mixed runtime teams or stop pursuing this segment.
- If Beads plus a small adapter provides most value, ship that adapter and make Loomplane a dependency service rather than another task tracker.
- If teams mostly need missing knowledge, use a retrieval/memory provider; do not relabel retrieval failures as dependency failures.
- Publish reproducible tasks, baseline configuration, total human effort, and raw outcome counts. Do not extrapolate memory benchmark scores into coding productivity claims.
- Claim neutrality, openness, and traceable revisions only when exercised. Never claim unique shared memory, automatic semantic correctness, or enterprise readiness.
